# Ablation Study Pipeline: Documentation

## Overview

The ablation study pipeline systematically evaluates multiple graph-based models (GCN, HGT, GBT, Causal, GCSN, DG2N, DGCRF) to compare their performance with and without data augmentation. This pipeline automates the entire workflow from data preparation through model training to metrics aggregation.

**Key Features:**
- Supports 7 different model architectures
- Compares no augmentation (level 0) vs. multiple augmentation levels (1, 2, ...)
- Automatically handles data slicing (Soot slicer with CF fallback)
- Uses shared augmentation directories to avoid redundant data generation
- Collects standardized training metrics (validation loss, test accuracy)
- Generates comparison reports across models and augmentation levels
- Enforces time limits to ensure studies complete within budget

## Architecture

The pipeline consists of three main components:

### 1. Study Orchestrator (`study_orchestrator.py`)

**Purpose**: Generates study plans and executable shell scripts for each model and augmentation level.

**What it does:**
- Creates a JSON study plan listing all model variants
- Generates numbered shell scripts (`01_slice.sh`, `02_resolve_normalize.sh`, etc.) for each variant
- Sets up shared directories for normalized slices and augmented data (to avoid duplicate work)
- Wraps model trainers in scripts that capture and emit standardized `metrics.json` files

**Key Design Decisions:**
- **Soot Slicer Default**: Uses Soot slicer by default; automatically falls back to Checker Framework (CF) if Soot produces no slices
- **Shared Augmentation**: Augmented slices are generated once per level and reused by all models
- **Metrics Wrapping**: Non-GCN models are wrapped in Python scripts that parse stdout/stderr to extract metrics (e.g., `val_loss`, `test_accuracy`) and write them to `metrics.json`

### 2. Sequential Runner (`studies/run_all_models_sequential.py`)

**Purpose**: Executes the study plan within a strict time budget, running models sequentially.

**What it does:**
- Loads the study plan generated by the orchestrator
- Selects augmentation level 0 (no augmentation) and the maximum available level for comparison
- Runs all steps for each model variant sequentially
- Enforces a global time limit (default: 6 hours)
- Stops gracefully if time runs out
- Automatically runs metrics aggregation at the end

**Execution Flow:**
1. For each model in the plan:
   - Select level 0 and max level variants
   - For each variant:
     - Execute scripts in order (`01_slice.sh` → `02_resolve_normalize.sh` → ... → `05_train.sh`)
     - Stop if deadline is exceeded

### 3. Metrics Aggregator (`studies/metrics_aggregate.py`)

**Purpose**: Collects metrics from all model runs and generates comparison reports.

**What it does:**
- Scans study directories for `models/{model}/metrics.json` files
- Extracts performance metrics:
  - **GCN, HGT, Causal, GCSN, DG2N, DGCRF**: Uses `best_val_loss` (lower is better)
  - **GBT**: Uses `test_accuracy` (higher is better)
- Generates comparison JSON files:
  - `ablation_overall_summary.json`: All models, all levels
  - `ablation_comparison_0_vs_1.json`: Direct comparison of no augmentation vs. level 1

## Pipeline Steps (Per Model Variant)

Each model variant (e.g., `gcn_aug0`, `hgt_aug1`) goes through these steps:

### Step 1: Slicing (`01_slice.sh`)
- Runs Soot slicer (or CF fallback) to extract code slices from the training dataset
- Slices are saved to `{variant_dir}/slices/slices_soot/` or `slices_cf/`
- Environment variables: `SOOT_SLICE_CLI`, `SOOT_JAR`

### Step 2: Resolve and Normalize (`02_resolve_normalize.sh`)
- Checks which slicer produced results (Soot preferred, CF fallback)
- Normalizes slices: copies all `.java` files to a flat directory structure
- Creates shared normalized slices directory (`shared_normalized_slices/`) if it doesn't exist
- Falls back to CF slicing if Soot produced no slices

### Step 3: Augmentation (`03_augment.sh`) [Only for aug1, aug2, ...]
- Runs semantic augmentation on normalized slices
- Generates augmented slices once per level in `shared_aug_slices_l{level}/`
- Reuses existing augmented data if already generated (avoids redundant work)
- Augmentation parameters:
  - `--variants {level}`: Number of variants per file
  - `--sequence-len 2`: Sequence length for transformations
  - `--max-depth 3`: Maximum transformation depth
  - Disabled transformations: `switch_statement`, `variable_operation`, `string_concatenation`, `numeric_literal`
  - Focus nodes: `control`, `dataflow`

### Step 4: CFG Generation (`04_cfg.sh` or `03_cfg.sh` for aug0)
- Generates Control Flow Graphs (CFGs) from Java slices (augmented or not)
- CFGs are saved as JSON files in `{variant_dir}/cfg/` or `aug_cfg/`
- Validates that CFGs were generated (exits with error if none found)

### Step 5: Training (`05_train.sh`)
- Trains the model on the generated CFGs
- Model-specific details:
  - **GCN**: Uses `gcn_train.py` with CLI arguments (`--epochs`, `--layers`, `--hidden`, `--dropout`, `--early_stop_patience`, `--metrics_path`)
  - **HGT, GBT, Causal, GCSN, DG2N, DGCRF**: Wrapped in Python scripts that:
    - Set environment variables (`CFG_OUTPUT_DIR`, `MODELS_DIR`, `SLICES_DIR`)
    - Run the model trainer
    - Parse stdout/stderr to extract metrics
    - Write `metrics.json` with standardized schema
- Training parameters:
  - Default epochs: 20-30
  - Early stopping patience: 5 (for GCN)
  - Timeout: 3600 seconds per model

## How to Run

### Prerequisites

1. **Environment Setup**:
   ```bash
   # Ensure Soot slicer is available (or CF fallback will be used)
   export SOOT_SLICE_CLI="${PWD}/tools/soot_slicer.sh"
   export SOOT_JAR="${PWD}/build/libs/GenDATA-all.jar"
   ```

2. **Required Files**:
   - `index1.out`: Warnings file from Index Checker
   - Project root with Java source files

3. **Python Dependencies**:
   - All model training scripts must be in the workspace root
   - `slice_dataset_tools.py` must be importable
   - Model-specific scripts: `gcn_train.py`, `hgt.py`, `gbt.py`, `causal_model.py`, etc.

### Step 1: Generate Study Plan

```bash
python study_orchestrator.py \
  --project_root /path/to/project \
  --warnings_file index1.out \
  --out_dir studies/all_models_ablation \
  --epochs 20 \
  --aug_levels 0 1 2
```

**Arguments**:
- `--project_root`: Root directory of the Java project to analyze
- `--warnings_file`: Path to Index Checker warnings file
- `--out_dir`: Output directory for the study (will contain all model variants)
- `--epochs`: Number of training epochs (default: 20)
- `--aug_levels`: List of augmentation levels to test (default: `0 1 2`)

**Output**:
- `{out_dir}/study_plan_all_models.json`: Study plan JSON
- `{out_dir}/{model}_aug{level}/scripts/*.sh`: Executable scripts for each variant

### Step 2: Run the Study

```bash
python studies/run_all_models_sequential.py \
  --plan studies/all_models_ablation/study_plan_all_models.json \
  --hours 6.0
```

**Arguments**:
- `--plan`: Path to study plan JSON (from Step 1)
- `--hours`: Maximum time budget in hours (default: 6.0)

**What Happens**:
- Sequentially runs each model for levels 0 and max level
- Executes all scripts in order for each variant
- Stops if time limit is exceeded
- Automatically runs metrics aggregation at the end

### Step 3: View Results

After the study completes, results are available in:

1. **Individual Metrics**:
   ```
   studies/all_models_ablation/{model}_aug{level}/models/{model}/metrics.json
   ```
   Each file contains:
   ```json
   {
     "start_ts": 1234567890.0,
     "end_ts": 1234568000.0,
     "duration_sec": 110.0,
     "epochs": 20,
     "exit_code": 0,
     "best_val_loss": 0.6234,  // or "test_accuracy": 0.851 for GBT
     "cfg_dir": "...",
     "out_dir": "..."
   }
   ```

2. **Aggregated Summary**:
   ```bash
   cat studies/all_models_ablation/ablation_overall_summary.json
   ```
   Shows metrics for all models at all levels.

3. **Comparison Report**:
   ```bash
   cat studies/all_models_ablation/ablation_comparison_0_vs_1.json
   ```
   Direct comparison of no augmentation vs. level 1 augmentation.

4. **Human-Readable Report**:
   ```bash
   python studies/generate_comparison_report.py
   ```
   Prints a formatted table comparing models.

## Metrics Interpretation

### For Loss-Based Models (GCN, HGT, Causal, GCSN, DG2N, DGCRF)
- **Metric**: `best_val_loss` (validation loss)
- **Interpretation**: Lower is better
- **Typical Range**: 0.5 - 2.0 (depends on model and dataset)

### For Accuracy-Based Models (GBT)
- **Metric**: `test_accuracy`
- **Interpretation**: Higher is better
- **Typical Range**: 0.0 - 1.0

### Comparison Logic
When comparing augmentation levels:
- **Loss models**: Level with lower `best_val_loss` is better
- **Accuracy models**: Level with higher `test_accuracy` is better
- The aggregator computes improvement percentage:
  - Loss: `((higher_loss - lower_loss) / higher_loss) * 100`
  - Accuracy: `((higher_acc - lower_acc) / lower_acc) * 100`

## Troubleshooting

### Issue: "No slices found after CF fallback"
- **Cause**: Both Soot and CF slicers failed to produce slices
- **Fix**: Check that the warnings file and project root are correct

### Issue: "No CFGs generated"
- **Cause**: CFG generation failed (no Java files or parsing errors)
- **Fix**: Check that normalized slices directory contains `.java` files

### Issue: Metrics are `null`
- **Cause**: Model training failed or metrics couldn't be extracted from output
- **Fix**: Check individual model training logs in `{variant_dir}/models/{model}/`

### Issue: Study times out before completing
- **Cause**: Time budget too small for the dataset size
- **Fix**: Increase `--hours` or reduce `--aug_levels` or `--epochs`

## Advanced Usage

### Running Only Specific Models

Edit `study_plan_all_models.json` and set `"supported": false` for models you want to skip, or modify `study_orchestrator.py` to only include desired models.

### Custom Augmentation Levels

Specify custom levels when generating the plan:
```bash
python study_orchestrator.py --aug_levels 0 1 3 5 ...
```

### Manual Script Execution

Individual scripts can be run manually for debugging:
```bash
cd studies/all_models_ablation/gcn_aug0/scripts
./01_slice.sh
./02_resolve_normalize.sh
./03_cfg.sh
./05_train.sh
```

### Re-running Metrics Aggregation

If metrics were added after the study completed:
```bash
python studies/metrics_aggregate.py
```

## Model-Specific Notes

### GCN
- Direct CLI support with `--metrics_path` flag
- Supports early stopping and scalable architecture (`--layers`, `--hidden`, `--dropout`)

### HGT
- Uses environment variables for configuration
- Metrics extracted from stdout by parsing "Val Loss:" lines

### GBT
- Uses environment variables for configuration
- Metrics extracted from stdout/stderr by searching for "accuracy" keyword

### Causal, GCSN, DG2N, DGCRF
- Use environment variables
- Metrics extraction varies by model (may require model-specific parsing logic in wrappers)

## Summary

The ablation study pipeline provides a complete automated workflow for:
1. **Generating** study plans for multiple models and augmentation levels
2. **Executing** model training within a time budget
3. **Collecting** standardized metrics across all runs
4. **Comparing** performance with and without augmentation

The system is designed to be robust (automatic fallbacks), efficient (shared augmentation), and comprehensive (supports 7 different model architectures).
